# 回收箱（与玩家绑定的自动结算容器）

一个普通的箱子或木桶，被某个玩家「认领」之后就会变成**回收箱**：
任何人往里面放东西，能换钱的自动卖到官方商店、能存建材银行的自动换成额度，
收益全部记到**认领它那个玩家**的账上。

- 代码：`plugins/economy/src/main/java/com/xiyuan/plugmc/economy/vault/`
- 命令：`/vault`（别名 `/huishouxiang`、`/collector`）
- 菜单：服务器菜单第 42 格「回收箱」

---

## 1. 玩家怎么用

| 操作 | 命令 | 说明 |
|---|---|---|
| 认领 | `/vault`（对着箱子/木桶右键执行） | 把这个方块变成自己的回收箱 |
| 认领（控制台/代理） | `/vault bind <x> <y> <z> <玩家>` | 坐标 + 玩家名，给管理端用 |
| 查状态 | `/vault info [x y z]` | 显示主人、建材额度、余额 |
| 立刻结算一次 | `/vault settle [x y z]` | 平时不需要手动敲，放进去就会自动算 |
| 解除 | `/vault unbind [x y z]` | 恢复成普通容器，里面东西不动 |

服务器菜单里第 42 格是「回收箱」，点进去是一个说明面板：
「绑定一个箱子」「绑定一个木桶」「怎么运作」「解除绑定」四块。

## 2. 结算规则

放进去的物品按**两道**依次过：

1. **建材银行**（`BankService.depositBatchFor`）—— 建材类物品换成银行额度，归到对应分类（stone / wood / wool / light …）。
2. **官方商店**（`ShopService.sellBatchFor`）—— 银行不收但商店标了 `sellable` 的，按当日价格卖出，扣税，钱进余额。

顺序是**先银行后商店**，理由是「建材银行是给建材准备的专用通道，先卖商店的话材料就变成普通金币，银行这条设计意图就落空了」。
两道都不收的（比如普通铁锭、带附魔/自定义名的物品）会**原样留在箱子里**。

- 走的是**绑定玩家**的每日限额（`dailyLimits`），不是投递者的。超出限额的那部分也留在箱里。
- 结算完成后如果绑定玩家在线，会收到一行汇总：「回收箱结算：建材 N 个 → 额度 X；卖出 M 个 → Y（税 Z）」。

## 3. 绑定存在哪

存在**方块自己的 PDC**（PersistentDataContainer）里，两个键：

```
economy:vault-owner        UUID 字符串
economy:vault-owner-name   当时用的名字（显示用，玩家改名不影响结算）
```

不额外维护坐标索引 —— 箱子被拆、被复制、被 `/setblock` 覆盖时，绑定跟着方块走，不会留悬空记录。

**★ 写 PDC 和读 PDC 必须用同一个 state 对象**。`block.getState()` 每次调用都返回一个新快照，
在 A 快照上改、再用 B 快照 `update()` 等于什么都没写。`VaultService` 里所有读写都走同一个
`containerOf(block)`。

## 4. 触发的时机

| 事件 | 行为 |
|---|---|
| 玩家关箱子（`InventoryCloseEvent`） | 排一次结算 |
| 漏斗往箱子里搬东西（`InventoryMoveItemEvent`，目标为回收箱） | 排一次结算 |
| 从回收箱往外抽（漏斗抽走） | **不结算**，不动账 |
| 手动 `/vault settle` | 立刻结算 |
| 方块被炸（`BlockExplodeEvent` / `EntityExplodeEvent`） | 把回收箱从爆炸名单里摘掉，免得被苦力怕顺手炸没 |
| 拆箱子（`BlockBreakEvent`） | 箱里还有东西时提示一句，不拦截 |

### 去抖

同一 tick 里漏斗可能连搬十几件，每件都触发一次 `InventoryMoveItemEvent`。
如果不拦，同一批会被拆成十几次结算。`settleLater` 用一个 `pending` 集合按方块去重：

```java
String key = block.getWorld().getUID() + "@" + x + "," + y + "," + z;
if (!pending.add(key)) return;                 // 已经排上队了，忽略
Bukkit.getScheduler().runTaskLater(plugin, () -> { pending.remove(key); settle(snapshot); }, 2L);
```

## 5. 三个必须记住的坑

### 5.1 `container.getInventory()` 是脱钩视图

```java
Inventory inventory = container.getInventory();   // ✗ 清空不落盘
inventory.clear();
```

`Container.getInventory()` 返回的是一个**不回写方块实体**的视图，清空动作不会保存。
结果是下一次读到的还是同一批物品 —— 漏斗每搬一件就整批重卖一遍，而且**箱里的东西一件没少**，
等于一个无限刷钱漏洞。

正确写法必须先拿快照、改完再 `update`：

```java
Inventory inventory = container.getSnapshotInventory();
inventory.clear();
for (ItemStack leftover : afterShop) inventory.addItem(leftover);
container.update(true, false);
```

### 5.2 先 clear 再放回，而不是先放回再 clear

顺序反了会把自己刚放回去的「两道都不收」的物品又结算一遍。

### 5.3 `plugins/economy/goods.yml` 里的 `sellable` 才是可回收清单

`GoodsConfig.matchSellable` 只认 `sellable: true` 的商品。仓库版 `goods.yml` 有 776 个商品，
其中只有 **diamond / ancient_debris / raw_copper / raw_iron / raw_gold** 五个标了 `sellable: true`。
测试服上如果放的是旧版 22 项 `goods.yml`，会出现「放进去什么都没发生」的假象
（`/vault settle` 后物品原封不动、也没有任何提示）—— 换 `goods.yml` 再重启即可。
`/eco reload` **不存在**，`/eco` 只认 `give|take|set|stats|doctor|selftest|audit|treasury|freeze|unfreeze|save|backup`。

## 6. 经济系统侧新增的接口

本来 `ShopService.sellBatch` 与 `BankService.depositBatch` 都只接受 `Player` 并且会自动给那个玩家发聊天消息。
回收箱的绑定玩家**可能已经离线**，所以各加了一条按 UUID 结算的通道，原来的 Player 版改成「调 UUID 版 + 发消息」：

| 新增 | 位置 | 说明 |
|---|---|---|
| `SellResult sellBatchFor(UUID, List<ItemStack>, List<ItemStack>)` | `ShopService` | 不发消息；返回 `soldCount / earned / tax / unsellable / limited` |
| `record SellResult(...)` | `ShopService` | 上者的返回类型 |
| `DepositResult depositBatchFor(UUID, String, List<ItemStack>, List<ItemStack>)` | `BankService` | 不发消息；返回 `count / points / kinds / gains / detail` |
| `record DepositResult(...)` | `BankService` | 上者的返回类型 |
| `used/remaining/canUse/consume(UUID, ...)` | `DailyLimitService` | 原 Player 版改写成委托给 UUID 版 |

## 7. 菜单接入的注意点

- `MenuHolder.Page` 加了 `VAULT`，`MenuManager.ACTIONS` 加了 `"vault_panel"`。
- **`execute(player, button)` 的 `switch` 必须也有 `vault_panel` 分支** —— 只加 `ACTIONS` 不加 `switch`
  会在点按钮时抛 `IllegalStateException: 未处理的菜单动作：vault_panel`，
  玩家那边表现为「点了没反应」，日志里才有这条异常。第一版就漏了这一处。
- 新增按钮走 `ensureVaultButton()` 的保守合并（先试默认槽位、被占找第一个空格、满了才 WARN），
  **绝不整体重置 `menu.items`**（那会抹掉管理员改过的菜单）。
