# 主城优化重建方案与实施记录

- 目标服务器：`minecraft:hub` 维度（虚空生成，48×48 大厅）
- 建筑基准层：`floor-y = 64`（地板），玩家站立面 `y = 65`
- 实施环境：本机测试服 `server\.testrun`（Paper 26.3，游戏口 25597 / RCON 25576）
- 生成方式：`blueprint_to_nbt.py` 出结构 → `place_plan.py` 按清单在 hub 维度批量摆放 → 逐项 `execute if block` 落块校验
- 全部新增建筑统一走 `HUB_STYLE`，材料与 `HubLobby` 程序生成的大厅**逐项对应**

## 二、优化方案

### 2.1 现状问题

1. **大厅是孤岛**。四面开门，门外是虚空 —— 玩家走出大门就往下掉（`y<0` 会被拉回出生点，但体验断裂）。
2. **北门到摊位之间只有一条 3 格宽走廊**，两侧是空的，视觉上像"悬空栈道"。
3. **东门出去直接是跑酷起点**，没有观赛落脚点，看别人跳跑酷只能站在走廊上。
4. **南门方向完全空置**，主城没有"街"的概念。

### 2.2 风格基准（`HUB_STYLE`）

所有新建筑严格使用大厅已有的那套材料，**不引入任何新色系**：

| 角色 | 材料 | 大厅里的出处 |
|---|---|---|
| 地面 | `smooth_quartz` | 大厅地板主材 |
| 分割线 | `polished_andesite` | 大厅地板每 6 格的分割带 |
| 基座 / 池沿 | `stone_bricks` | 大厅外墙下段、喷泉外圈 |
| 墙体 | `smooth_quartz` | 大厅外墙中上段 |
| 立柱 | `quartz_pillar[axis=y]` | 大厅墙体柱子、内圈四角柱 |
| 装饰块 | `chiseled_quartz_block` | 与石英柱同族，仅用于构件顶端 |
| 窗 | `glass_pane` | 大厅外墙 `y=69..71` |
| 主灯 | `sea_lantern` | 大厅柱顶、地板灯带 |
| 辅灯 | `lantern[hanging=false]` | 大厅内圈柱 `y=72` |
| 绿化 | `azalea_leaves[persistent=true]` + `oak_log[axis=y]` | 新增，唯一非石英元素（树池），与石砖池沿呼应 |

**统一手法**（每个构件都遵守，这是"彼此统一"的具体保证）：
- 所有构筑物都坐落在石砖基座/池沿上，基座一律高出铺装 1 格；
- 所有柱式构件一律 `stone_bricks 底座 → quartz_pillar 柱身 → sea_lantern 柱顶`；
- 所有顶盖一律平滑石英，边缘外挑 1 格；
- 所有吊灯一律 `lantern[hanging=true]` 挂在顶盖正中。

### 2.4 四片街区（保留 / 新建 / 移位的决策）

| 街区 | 范围 | 决策 | 理由 |
|---|---|---|---|
| **大厅本体** | `x,z ∈ [-24,24]` | **完全保留，一格不动** | 含 `isBuilt` 判定方块 `(0,68,0)` 海晶灯，重建会让插件判定失效；大厅本身比例与材料已经是这套风格的基准 |
| **跑酷赛道** | `x 25..118`, `z -3..3` | **完全保留，一格不动** | 含 `isBuilt` 判定方块 `(34,64,0)` 金块；跳台间距 4 格是难度设计，改动即改玩法 |
| **小游戏摊位** | `x -17..17`, `z -43..-37` | **完全保留，一格不动** | 柜台坐标是右键判定表的键，移位必须改 Java 代码并重启，风险高于收益 |
| **南大街**（新） | `x -22..22`, `z 25..63` | **新建** | 南门原本空置；补一条 38 格长的商业街，让主城有"城"的体量 |
| **西广场**（新） | `x -58..-25`, `z -20..18` | **新建** | 西门原本空置；作为主城第二客厅，放喷泉 + 铺面 |
| **北庭**（新） | `x -22..22`, `z -31..-25` | **新建** | 补北门到摊位之间那段空场，把 3 格宽走廊扩成 23 格宽前庭 |
| **东观赛区**（新） | `x 25..34`, `z 1..16` | **新建** | 跑酷起点旁加观赛落脚点，不碰赛道 |
| **环廊**（新·二期） | 大厅外墙一圈，`|x|` 或 `|z| ∈ [25,28]` | **新建** | 一期的四片街区各接一道门，斜着走会掉虚空；补一圈 4 格宽步道把四条街串成闭环 |

**没有任何原有建筑被移位。** 三处"保留"区都含插件运行时判定的关键方块（`isBuilt` 标记、右键判定键），改动它们会破坏功能 —— 这正是不移位的技术理由，不是保守。

### 3.3 与既有建筑的衔接（防踩空）

铺装范围不是随手定的，每一片都接到大厅外墙或既有走廊上，实测确认：

| 衔接处 | 实测结果 |
|---|---|
| 南门 → 南大街 | `z=24` 大厅地板、`z=25` 起新铺装，连通无断口 |
| 西门 → 西广场 | `x=-24` 大厅地板、`x=-25` 起新铺装，连通 |
| 北门 → 北庭 | `z=-24` 大厅地板、`z=-25..-31` 新铺装、`z=-32` 摊位走廊，**上下两条走廊都接上了** |
| 东门 → 东观赛区 | `z=0` 起跑酷走廊（`x 25..31`），铺装从 `z=1` 起，`z=1..16` 与走廊连成一片 |

**环廊**：`floor` 用四段矩形（`floor` 支持单个矩形或矩形数组，本次为此扩展）：

```json
"floor": [
  {"x0": -28, "z0": -28, "x1": -25, "z1": 28},   // 西段
  {"x0":  25, "z0": -28, "x1":  28, "z1": 28},   // 东段
  {"x0": -24, "z0": -28, "x1":  24, "z1": -25},  // 北段
  {"x0": -24, "z0":  25, "x1":  24, "z1":  28}   // 南段
]
```

四段首尾相接、紧贴大厅外墙（外墙在 `±24`，环廊占 `25..28`），把四条街串成闭环。摆件：四角灯柱 `(-26,-26) (26,-26) (-26,26) (26,26)`，四面中段树池 `(-27,0) (27,0) (0,-27) (0,27)`。

实测 `y=64` 全环扫描（`x/z -30..30` 步长 4）：**从 `(-22,-30)` 到 `(22,30)` 整片连通**，只有最外圈 `|x|=30` 或 `|z|=30` 的角落是空气 —— 那是铺装边界之外，属预期。

### 7.4 线上才发现、本地没暴露的三个 bug

1. **`/bazaar rebuild` 只清摊位不清分配器** —— 重建后 `bazaar status` 显示 `0 / 24`、`bazaar list` 显示「（还没上摊）」。因为 `distributor.assigned` 仍记着玩家占位，`sync()` 走 refresh 分支，而 `stalls.refresh()` 找不到状态时直接返回。修法：`BazaarDistributor.reset()` 清 `assigned`/`decorOf`/`lastOverflow`，`rebuild()` 里与 `releaseAll()` 成对调用。
2. **三套装饰的地毯方块 id 不存在** —— `minecraft:oak_carpet` / `spruce_carpet` 在 26.3 没有（地毯只按颜色分）。启动日志刷 12 条「摊位装饰里的方块写法无效，已跳过」。改成 `brown_carpet` / `gray_carpet`，`quartz` 套的 `white_wool` 统一成 `white_carpet`。
3. **建摊早于铺地导致地毯被盖掉** —— 重启时 bazaar 先建摊（快照记的是 `air`），之后 `place_plan` 才铺地，地毯被铺装压住。地毯层**不能**改成 `y+1` 绕开：y=64 就是「地面最上面一层」，摊位压在铺装上、撤摊时还原成 `smooth_quartz` 才是正确语义。正确做法是**先铺地再建摊**，或事后 `/bazaar rebuild`（快照重记）。
4. **人偶与招牌在建摊时写成 `setPersistent(false)`** —— 部署收尾把 `forceload` 清掉、区块一卸载，这些实体就被当成"可随手丢弃"直接删除，而且不会重新生成。表现是 `bazaar list` 里还有人摆摊、3 个固定摊位也在，但 `@e[type=mannequin]` 一个都查不到。修法：全部改成 `setPersistent(true)`；同时给 `refresh()` 加 `ensureActors()`，每轮刷新检查人偶/招牌还在不在，丢了就地补一个（位置由摊位序号决定，不会跳格），并在补之前先判 `world.isChunkLoaded(...)` —— 否则"区块没加载"会被误当成"实体被杀了"，每 40 tick 补一个新的，还逼着服务端把这片永远读进内存。
   顺带修 `sweepOrphans()`：实体是随区块从磁盘读出来的，区块没加载就扫不到上一轮遗留的，所以清扫前先把所有摊位的区块点一遍（`loadStallChunks`），否则遗留人偶会和新建的那个重复。

### 7.5 收尾注意

- 部署时为探测区块加过 `forceload add -60 -64 60 64`，落地完成后已用 `forceload remove all` 全部清掉。主城与商业街**不依赖强制加载**：区块卸载后建筑方块留在存档里，人偶与招牌已改成持久化实体、也跟着区块一起存盘，玩家走过去自然会加载出来。

## 八、建筑师改了建筑、重启后全被还原（已修）

### 8.1 现象

建筑师（有 `hub.build` 权限的管理员）在大厅里改方块、加装饰，当时都生效；**服务器一重启，改动全部消失，回到插件刚生成时的样子**。日志里除了正常的 `主城大厅 已启用（…）` 什么都没有，看不出异常。

### 8.2 根因

`HubLobby.isBuilt()` 用**一颗方块**当「大厅建过没有」的判据：

```java
// 改前
public static boolean isBuilt(World world, HubConfig config) {
    return world.getBlockAt(0, config.floorY() + 4, 0).getType() == Material.SEA_LANTERN;
}
```

喷泉顶端那颗海晶灯 `(0,68,0)` 一旦不是海晶灯 —— 被拆、被换成别的水晶、铺地时被顺手盖住 —— `ensureLobby()` 就认为「还没建」，直接调 `HubLobby.build()`：

```java
clearTexts(...);      // 删掉 64×48×64 范围内所有 TextDisplay
clearBlocks(...);     // 半径 25、高 13 的整片方块 → 全部 AIR
buildFloor/Walls/Roof/InnerPillars/spawnTexts(...);
```

于是建筑师今天做的一切被整片抹掉。`ParkourCourse.isBuilt()` 是同一个毛病：拿起点那颗 `GOLD_BLOCK` 当判据，一换就重摆赛道。

### 8.3 复现（本机测试服）

1. `execute in minecraft:hub run setblock 0 68 0 minecraft:air`（拆掉那颗灯）
2. 放两个自己的标记：`setblock 5 65 5 gold_block`、`setblock 8 65 8 diamond_block`
3. `stop` → `start-detached.ps1` 重启
4. 结果：**两个标记方块都不见了，海晶灯自己回来了**，`hub info` 显示「大厅已生成：是」

### 8.4 修法

**「建没建过」不再看世界里的方块，改成插件数据目录里的文件** `plugins/hub/lobby-built.yml`：

```yaml
built: true
parkour-built: true
floor-y: 64
radius: 24
```

- 新增 `HubMarker`：`isBuilt()` / `isParkourBuilt()` / `markBuilt(config)` / `markParkourBuilt()` / `migrateFromLegacyBlock(world, config)` / `warnIfGeometryChanged(config)`。
- `HubWorld.ensureLobby()` 改为读 `marker.isBuilt()`；只有真的重建时才 `markBuilt()`。想重建只能显式 `/hub build`。
- `HubPlugin.ensureParkour()` 改为读 `marker.isParkourBuilt()`。
- **老存档平滑升级**：文件不存在、但世界里的旧标记方块还在 → `migrateFromLegacyBlock()` 补写文件、**不重建**。线上就是这样升级的，日志一行 `已把「大厅已生成」标记写入 lobby-built.yml（沿用世界里的老标记方块，没有重建）`。
- `floor-y` / `radius` 被改过时只打 WARNING、**不自动重建** —— 改两个数字就清掉建筑师的作品，正是这个功能最不该有的行为。
- `hub check` 第一行改成「生成标记（lobby-built.yml 已记录/缺失）」，把「建没建过」和「结构件是否完好」分开：原来那条「喷泉标记（海晶灯）」名字改成「喷泉顶灯」，它只是装饰件的检查，红了也**不会**导致重建。

### 8.5 顺带修掉的两个「清理范围越界」

`build()` 的重建一旦发生，除了清方块还会删实体，而它的范围原本是硬编码的大数字，**会连带清掉主城外围的街区**：

| 位置 | 改前 | 改后 | 为什么 |
|---|---|---|---|
| `HubLobby.clearBlocks` | `radius + 1`（=25） | `radius`（=24） | 半径 24 的大厅外缘正好贴光环廊（`|x|` 或 `|z|` ∈ 25~28）与西南角商业街（`z` 从 24 起），多清一格就抹掉街区铺装 |
| `HubLobby.clearTexts` | `getNearbyEntities(center, 64, 48, 64)` | `getNearbyEntities(center, radius+1, ROOF_OFFSET+6, radius+1)`，且跳过带 `plugmc_bazaar` 标签的实体 | 旧范围覆盖商业街（`x -60..-24, z 24..62`），重建大厅会把摊位招牌、货台展示一起删掉 |

### 8.6 验证

| 场景 | 改前 | 改后 |
|---|---|---|
| 拆掉 `(0,68,0)` 海晶灯 → 重启 | 整片重建，自放方块消失 | 方块**全部保留**，`hub check` 只报「喷泉顶灯 ✘」 |
| 拆掉跑酷起点 `(34,64,0)` 金块 → 重启 | 赛道按默认布局重摆 | `(34,64,0)` 仍是空气、终点 `(118,70,0)` 仍是 `DIAMOND_BLOCK`，**没有重摆** |
| `hub info` | 靠方块判断 | 读 `lobby-built.yml`，`built` / `parkour-built` 分别记录 |

线上实测（`bb911bbb`）：放 `gold_block` 到 `(10,66,10)`、把 `(0,68,0)` 改成空气 → `power('restart')` → 重启后 `if block 10 66 10 minecraft:gold_block run seed` **命中**、`if block 0 68 0 minecraft:air run seed` **命中**，编辑保住了。测试完已把 `(0,68,0)` 还原成 `SEA_LANTERN`、`(10,66,10)` 清成空气，`hub check` 生成标记 / 喷泉顶灯全 ✔，`bazaar check` 10/10。

### 8.7 以后给建筑师的约定

- **想改就改**，不用再担心那颗海晶灯。`hub check` 里「喷泉顶灯」变红只是提示喷泉不完整，不影响任何东西。
- **真的要从零重来**才执行 `/hub build`（会清空半径 24 内、`floor-y` 以上的全部方块）—— 这条命令才是唯一会抹掉作品的操作。
- 删 `plugins/hub/lobby-built.yml`（或把 `built` 改成 `false`）同样会触发重建，等价于 `/hub build`。

## 九、两块排行榜：敲钟榜与跑酷榜

两块榜的共同规则：**没参与过的人不占名次**，一行都不显示；人数超过 `rows`（默认 10）时最后一行变成「…还有 N 位」。

### 9.1 敲钟榜

钟点在 `(0, 66, 58)`（`minecraft:bell[attachment=floor,facing=south]`，钟亭正中）。玩家每右键一次，次数 +1，屏幕下方飘一行 `敲钟 N 次`。

- 计数走 `org.bukkit.event.block.BellRingEvent` 的 MONITOR 阶段，**只认 `event.getEntity() instanceof Player`** —— 村民撞钟、活塞推钟都不算。
- **200ms 节流**：一次右键会同时触发主手和副手两个事件，不节流就一次算两次。
- 数据落在 `plugins/hub/bell.yml`，30 秒或关服时落盘：

```json
{ "23d56995-3fc6-367d-a490-5dc1ca93f631": { "name": "ShopTester", "count": 3 } }
```

管理命令：`/hub bell top` 看前 10、`/hub bell board` 重建榜牌、`/hub bell reset <玩家名>` 清零某人的记录（后两条要 `hub.admin`）。

### 9.2 跑酷榜

数据不是新统计的，直接读已有的 `ParkourManager`（`plugins/hub/parkour.yml` 里本来就是 `name` + `millis`）。跑完一圈 `finish()` 落盘后立刻 `parkourBoard().refresh()`，榜牌当场变，不等定时器。


管理命令：`/hub parkour board` 重建榜牌（要 `hub.admin`）。

### 9.3 榜牌是怎么做出来的

两块榜都是 `TextDisplay` 实体，挂在世界坐标上，不是方块、不进存档方块表：

- 打 `plugmc_bell_board` / `plugmc_parkour_board` 标签，方便查找、重建、以及在 `clearTexts` 里避开；
- `setPersistent(true)` —— 这条很关键，`false` 的展示实体在区块卸载时会被当成可丢弃对象**永久删除**且不重建；
- `Billboard.CENTER` + `setSeeThrough(false)` + `setDefaultBackground(false)`，从任何角度都是正对玩家的一整块字。

### 9.4 踩过的三个坑

**① `world.getEntities()` 只返回已加载区块里的实体。** 刚开服时起点那一带还没加载，`findBoard` 扫不到旧牌，于是又建一块 —— 重启三次就叠出三块牌，位置完全重合、看着像字糊了。修法是查之前先 `world.getChunkAt(cx, cz)` 把区块点开，并且 `findBoard` 只留第一块、其余 `remove()`。

**② `plugins/` 里同时放 `hub-0.1.3.jar` 和 `plugmc-hub-0.1.3.jar` 会静默加载旧那份。** 启动日志只有一行 `[ModernPluginLoadingStrategy] Ambiguous plugin name 'hub'`，然后跑的是老代码 —— 表现是「代码改了、行为没变」。部署前必须确认同名插件只剩一个 jar。

**③ 传送不会触发跑酷计时。** 计时靠 `ParkourMoveEvent` 里判脚下的垫方块，`/astp` 直接把人放到起点方块上时，因为起止格没变（`from == to`）会被跳过。验证要用 `/hub parkour`（走 `join()` 直接开始计时），或者干脆从起点上方几格落下来。
